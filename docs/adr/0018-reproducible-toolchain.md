# ADR-0018 — A build that resolves to the same thing twice

- **Status:** Accepted
- **Date:** 2026-08-24

## Context

Every dependency in `backend/pyproject.toml` was declared as a floor — `django>=5.0`, `celery>=5.3`,
`ruff>=0.6`. That is the right thing for a library, which must coexist with whatever its consumer
already has, and the wrong thing for an application, which is deployed. It meant CI resolved the tree
fresh on every run, so a green pull request and the red one that followed it an hour later could
differ by an upstream release nobody in this repo had chosen.

That is not hypothetical here. **#71** was exactly it: Django 6.1 removed `django.utils.cache.cc_delim_re`,
which every released DRF still imports, and an unbounded `django>=5.0` resolved the pair that fails at
import. The fix was a ceiling in `pyproject.toml` — correct, and it only closes the one door that had
already been walked through.

Three symptoms, one cause:

- **CI and a developer machine installed different trees**, so "works locally" and "passes CI" were
  independent claims about different software.
- **The lint gates disagreed with each other.** `.pre-commit-config.yaml` pinned ruff 0.6.9 while CI
  installed `ruff>=0.6` and got 0.16 — versions two years apart, with different default rulesets.
  The repo was already carrying a `[tool.ruff.lint] select` pin to survive that gap.
- **A fresh clone could not run the documented commands.** README went straight to `make test`, which
  called a bare `pytest` and died with `command not found` on a machine that had never installed
  anything.

## Decision

**A compiled, hash-pinned lockfile is the single description of the backend environment.**
`backend/requirements.lock` (runtime) and `backend/requirements-dev.lock` (runtime + dev) are
generated by `pip-compile` from `pyproject.toml`, with `--generate-hashes`. `pyproject.toml` keeps its
floors and its reasoning — it says what is *allowed*; the lock says what is *installed*.

**Everything installs from the lock:** `make bootstrap` into `backend/.venv`, the CI job, and the
backend image. Each does `pip install --require-hashes -r <lock>` followed by
`pip install --no-deps -e .`, because letting pip re-resolve from the floors at the editable-install
step would reintroduce the float one line after removing it.

**pip-tools, not uv or Poetry.** The deciding property is the *install* side, not the resolve side: a
pip-compile lock is a plain requirements file, so the image, CI and a venv consume it with the pip
they already have and no new tool enters the runtime. uv resolves faster and does universal
(cross-platform) resolution, which is genuinely better — but it would have to be installed in the
image and in CI to be the thing that reads the lock. The resolver only runs when a dependency
changes; the installer runs on every build.

**Locks are compiled inside `python:3.12-slim`, via `make lock`.** pip-compile resolves for the
platform and interpreter it runs on. Compiling on a developer's macOS/arm64 would describe an
install that nothing in this project ever performs. The container is the environment CI and
production actually install into, so the resolution is done there.

**Linter versions exist in exactly one place.** The ruff and black hooks in `.pre-commit-config.yaml`
became `local` / `language: system` hooks that execute `backend/.venv/bin/{ruff,black}`. A remote
hook carries a `rev:`, and a second place to write a version is a second place for it to be wrong.
The remaining remote hooks are whitespace and YAML hygiene, which cannot disagree about whether code
passes lint. For the same reason `[tool.black] target-version` is now stated rather than inferred
from whichever interpreter invoked it.

**`make bootstrap` is the documented first step, and the other targets require it.** `test` and
`lint` invoke `backend/.venv/bin/...` by absolute path and declare that binary as a prerequisite, so
make fails with *"run 'make bootstrap'"* instead of `pytest: command not found`. `make dev` stays
independent — it is pure Docker and builds from the same lock.

**Correctness of the lock is tested; freshness is not.** `backend/tests/test_toolchain.py` asserts,
offline, that both locks are fully pinned and hashed, that **every pin satisfies the specifier
`pyproject.toml` declares** (the #71 ceiling, now unshippable), that the two locks agree on every
shared package, that the installed ruff and black are the versions the lock chose, and that no
pinned remote ruff/black hook has reappeared. Deliberately *not* checked: whether re-running
`pip-compile` today would produce a different file. That check requires the network and goes red
whenever any transitive dependency publishes a release — turning "someone else shipped something"
into "your pull request is broken", which is the failure mode this ADR exists to remove.

## Consequences

**What this buys.** Two builds of the same commit install the same bytes, verified by hash. A
dependency change is a reviewable diff in a tracked file rather than an invisible event on PyPI. CI
and a bootstrapped machine run the same linters, so a clean local run predicts a clean CI run. The
Docker dependency layer stops being invalidated by code edits, because the lock is copied and
installed before the source is. And the `pyproject.toml` bounds are now enforced by a test rather
than by the resolver's good behaviour.

**What it costs.** Dependency upgrades are no longer automatic: nothing moves until someone runs
`make lock` and reviews the diff, so a security release now needs a deliberate act. That is the
trade being made — a stale dependency is a decision, whereas the alternative was an unannounced
upgrade in the middle of an unrelated change.

`make lock` needs Docker, which is a heavier requirement than `pip-compile` on the host — accepted,
because a lock compiled on the wrong platform is worse than no lock: it looks authoritative and is
not.

The pre-commit linter hooks now require `make bootstrap` to have run. That is a real ordering
constraint, and it is the same one `make test` already has.

**Not addressed here.** The frontend was already reproducible via `package-lock.json` and `npm ci`;
`.nvmrc` and a Node-major check in `bootstrap` were added so the failure on an old Node names the
fix, but nothing about the JS resolution changed. Automated dependency updates (Dependabot or
Renovate opening `make lock` pull requests) are the natural follow-up and are not part of this
change.
